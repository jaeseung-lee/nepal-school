# 1부 — 내린 결정 (185건)

## Pre-flight 충돌 스캔

- T2의 대학 목록 검증은 **id 기준**으로 한다 — `universities.json`의 각 항목은 `{"id", "name_ko"}`를 갖고, 테스트는 (a) 그 id가 `partnership-network.ts`에 `kind: "university"`로 있고 status가 `planned`가 아님, (b) `name_ko`가 `company/messages/ko.json`의 `network.institutions.<id>.name`과 일치함을 본다 — 이유: `partnership-network.ts`에는 한글 대학명이 없고 id만 있다(실제 파일 확인). 계획의 `assert n in ts`는 그대로 두면 반드시 실패한다. 틀렸을 때의 비용: 검증이 id만 보게 되어 ko.json의 오타를 못 잡는다(테스트 (b)가 그 구멍을 덮는다).
- T4는 `scripts/facebook/config.py`를 **수정 대상에 포함**한다 — `REQUIRED_PROMPT_DIRECTIVES: tuple[str, ...]` 상수를 거기에 추가한다 — 이유: Step 3이 이미 그렇게 지시하는데 Files 목록에 없어 구현자가 상수를 validate.py에 숨길 수 있다. 틀렸을 때의 비용: 상수 위치가 달라질 뿐 동작은 같다.
- T5의 용어집 경고는 **"source_ko에 용어집 항목의 한국어 표기가 나오는데 body_local에 같은 항목의 해당 언어 표기가 없으면 warning"** 으로 한정한다 — 이유: 계획의 "다르게 표기되면"은 판정 기준이 없어 구현자마다 다른 것을 만든다. 틀렸을 때의 비용: 현지어 쪽 오표기 중 한국어 원문에 대응어가 없는 경우를 놓친다. 경고일 뿐 예약을 막지 않으므로 손해가 제한적이다.

## Task 1

- 테스트 명령을 `uv run --python 3.11 --with pytest pytest scripts/facebook/tests/ -v` 로 고정한다 — 시스템 기본이 3.10.6이라 핀이 없으면 테스트만 3.10에서 돌고, 저장소 기존 uv 스크립트와 계획 전역 제약(≥3.11)이 선언한 실행 환경과 어긋난다. 나중 작업이 3.11 API를 쓰는 순간 깨진다. uv에서 3.11.12 확보 확인. 틀렸을 때의 비용: 테스트 첫 실행이 조금 느려지는 것뿐.
- DEFAULT_POST_TIME_JST = 19:00 유지 — 스펙은 "JST 저녁"만 정했고 19시는 그 범위 안이다. 틀렸을 때의 비용: **설정값 한 줄이 아니다.** 이 상수를 읽는 코드가 하나도 없고 `publish_at`은 전부 플랜 JSON에서 오므로, 시각을 바꾸는 비용은 플랜 작성 지침 한 줄과 그 달 플랜의 `publish_at` 서른 줄이다. (최종 검토 M2에서 바로잡음: 죽은 상수 둘과 그것을 보호처럼 보이게 한 동어반복 시험을 지우고, 「JST 저녁(기본 19:00)」을 운영 문서 「플랜 작성 지침」 1항에 직접 적었다.) Note: `.env`는 gitignore라 워크트리에 없다. 토큰은 Task 8·10 실행 시점에만 필요하고 테스트는 환경변수 경로로 덮으므로 조치 없음.
- 최종 테스트 명령은 `uv run --python 3.11 --isolated --with pytest pytest scripts/facebook/tests/ -v` — 이유: 핀 없이는 3.10에서 돌고, 핀만으로는 이 머신에서 깨진다. 둘 다 직접 확인함. 틀렸을 때의 비용: 다른 머신에서 `--isolated`가 불필요할 수 있으나 해롭지 않다.
- Important #1(환경변수가 .env를 가림)은 **내 지시에서 나온 것**이다(디스패치에 "prefer an already-set FB_PAGE_TOKEN env var"라고 썼다). 스펙 원문은 "토큰은 `.env`에 두고 커밋하지 않는다"로 *커밋 금지*가 요지이고, 내 계획이 이를 "`.env`에서만 읽는다"로 더 좁게 옮긴 것이 충돌의 원인이다. 환경변수 경로는 유지한다 — 워크트리에 `.env`가 없고 CI·다른 환경에서 필요하다. 다만 검토자가 지적한 진짜 위험(회전된 토큰을 낡은 셸 변수가 조용히 가림)은 제거한다: **두 출처가 모두 값을 주고 서로 다르면 한국어 오류로 멈춘다.** 조용한 가림이 사라지므로 위험이 해소된다. 계획의 전역 제약 문구도 스펙 원문에 맞춰 고친다. 틀렸을 때의 비용: 두 출처를 일부러 다르게 두고 쓰려던 사람이 막힌다(그런 용법은 없다).
- Minor #2(OSError·UnicodeDecodeError가 영어 OS 메시지로 샘)와 #3(PEP8 빈 줄)은 수정 라운드에 포함한다 — #2는 "오류 메시지는 한국어" 전역 제약 위반이고 #3은 내가 지시한 shim 제거의 잔여물이다. 나머지 Minor(#1 인용부호+인라인주석, #4 비문자열 value 메시지, #5 fromisoformat 관대함, #6 죽은 sys.path 삽입)는 이월해 최종 검토에서 분류한다.
- 커밋 trailer의 "Co-Authored-By: Claude Opus 5"는 서브에이전트가 Sonnet으로 돌았어도 그대로 둔다 — 세션에 주어진 귀속 지시가 그 문자열을 쓰라고 명시한다. 틀렸을 때의 비용: 귀속 줄이 실제 실행 모델과 다르게 남는다. Note: 검토자의 ⚠️ "테스트 출력 경고 없음"은 컨트롤러가 직접 확인함 — `42 passed in 0.04s`, 경고 없음.
- 계획의 모든 테스트 명령을 `uv run --python 3.11 --isolated ...` 로 통일하고, Task 2의 RED 기대값을 FileNotFoundError → FactsError로 정정했다 — 이유: Task 1이 OS 오류를 한국어 FactsError로 감싸면서 Task 2 브리프의 예상 실패 메시지가 실제와 달라졌다(구현자가 지적). 브리프 2~10 재생성함. 틀렸을 때의 비용: 없음, 문서 정합성 수정.

## Task 2

- 컨트롤러 자체 점검에서 결함 발견 — `tuition_*` 11건의 source_url이 전부 academyinfo 검색 쿼리 주소라 값을 되짚을 수 없다(HTTP 200은 검색 엔드포인트 생존만 증명). 값을 실제로 표시하는 URL(대학알리미 공시 상세, data.go.kr 표준데이터 15107738, 또는 대학 자체 등록금 페이지)로 교체하고, 불가하면 해당 사실을 drop하도록 사전 수정 지시. 틀렸을 때의 비용: 등록금 사실 일부가 사라져 게시물에서 금액을 못 쓴다(설계상 안전한 방향).

## Task 3

- 대학명 표기 — `body_local`에는 **한국어 대학명이 그대로 들어가야 한다**. 플랜 생성 시 그 옆에 현지 문자 설명을 덧붙이는 것은 허용한다. 이유: Task 5의 대학 allow-list·맥락 검증이 본문에서 이름을 찾아내야 하는데, 음차나 현지어 의역만 있으면 검증이 성립하지 않는다. 또 학생이 실제로 지원·검색할 때 쓰는 것은 한국어 교명이다. Task 5는 한국어 이름으로 매칭한다. 틀렸을 때의 비용: 미얀마어·네팔어 문장 안에 한글이 박혀 읽기 불편하다. 해소책은 검증된 영문 교명을 Task 2식으로 조사해 넣는 것이며, 이번 범위 밖이므로 사용자에게 후속 후보로 보고한다.
- Task 4 이미지 용량 상한 — 브리프 본문의 "8MB"는 `config.MAX_IMAGE_BYTES`(8 * 1024 * 1024, 즉 8 MiB)를 가리키는 줄임말로 읽는다. 검증 코드는 숫자를 다시 쓰지 않고 `config.MAX_IMAGE_BYTES`를 import해 쓴다. 이유: 상한을 한 곳에서만 고치게 하는 것이 Task 1의 설계 의도다. 틀렸을 때의 비용: 페이스북 실제 상한이 8 MB(십진)라면 8,000,000~8,388,608바이트 구간의 이미지가 업로드 단계에서 거부되고, 그때 config 한 줄만 고치면 된다.
- Task 4 용량 테스트 — 8 MiB 넘는 테스트 파일은 `open(..., "wb").truncate(n)`로 희소 파일을 만들어 즉시 생성한다. 실제 바이트를 쓰지 않는다. 이유: 테스트 한 건이 8 MiB를 디스크에 쓰면 전체 스위트가 느려지고 CI에서 쓸 이유가 없다. `Path.stat().st_size`는 희소 파일에서도 논리 크기를 돌려주므로 검증 대상 동작은 그대로 재현된다. 틀렸을 때의 비용: 없음에 가깝다 — 구현이 `st_size` 대신 실제 읽기로 용량을 센다면 테스트가 먼저 깨져서 드러난다.
- `plan.month` 미사용 — 검토자가 찾은 공백(month를 게시일과 대조하는 주체가 어느 task에도 없음)을 **Task 4가 가진다**. 플랜과 task-4 브리프에 `test_게시일이_plan_month_밖이면_오류`(code `"월밖"`)를 추가하고 기대 통과 수를 13→14로 고쳤다. 이유: Task 4가 이미 게시일 연속성을 보므로 같은 함수에서 월 포함 여부를 보는 것이 가장 짧고, month가 장식으로 남으면 11월 플랜에 12월 날짜가 섞여도 아무도 못 잡는다. Task 9의 예약 창 검사는 "지금부터 75일" 기준이라 12월 날짜를 통과시킨다. 틀렸을 때의 비용: 월을 걸치는 플랜을 의도적으로 만들려 할 때 검증이 막는다 — 설계상 월 단위 운영이므로 그런 플랜은 없다.

## Task 4

- 구현자 우려 3(소재 교차 배치) — **고친다.** `A-vi, B-vi, A-my, B-my, A-ne, B-ne`가 통과하는 것은 실제 구멍이고 구조 문제라 Task 4 범위 안이다. 새 코드 `소재분산`을 추가하고, 한 소재의 세 게시물 index가 `n, n+1, n+2`로 이어붙어 있는지로 판정한다(날짜 연속성은 이미 전체 목록에서 보므로 재계산하지 않는다). 이유: 스펙의 "소재 하나당 베트남-미얀마-네팔, 하루 1건"은 사흘 연속을 뜻한다. 사용자의 원문도 "소재 하나당 베트남 - 미얀마 - 네팔 이렇게"다. 틀렸을 때의 비용: 의도적으로 소재를 섞어 올리고 싶어지면 검증이 막는다 — 설계상 그런 운영은 없다.
- 생존 변이(MAX_IMAGE_BYTES 값이 어디에도 고정되지 않음) — `test_config.py`에 값 고정 테스트를 추가한다. "숫자를 다시 쓰지 말라"는 내 지시는 검증 로직에만 적용되며, 상수 값을 config 테스트에서 고정하는 것은 그 반대 관심사다. 틀렸을 때의 비용: 없음.
- 구현자 결정 1~9 전부 인정 — `.jpeg` 허용, 프롬프트 문구 전체 대조, `이미지경로` 가드, 대소문자 무시 중복, 소재 단위 finding을 첫 게시물에 붙임, 언어누락/언어순서 분리, OSError→이미지없음, 게시물 타임존 기준 날짜, 벽시계 비의존 만료 테스트. 특히 `이미지경로` 가드는 브리프 밖이지만 폴더 밖 파일을 "있다"고 보증하는 것을 막으므로 받는다.
- 검토자 ⚠️ "본문에 수치가 있는데 `fact_keys`가 비면 아무도 못 잡는다" — **Task 5가 가진다.** `validate_facts`는 `post.fact_keys`만 순회하므로 빈 튜플이면 사실 검사를 전부 건너뛴다. 이것이 설계의 첫 안티골("검증되지 않은 학비·비자·아르바이트 시간 수치가 현지어로 나가는 것")에 도달하는 유일한 경로다. Task 5 플랜·브리프에 `test_출처없는_수치가_본문에_있으면_경고`(code `출처없는수치`, severity `warning`)와 `test_fact_keys가_있으면_수치가_있어도_통과`를 추가하고 기대 통과 수를 8→10으로 고쳤다. 판정은 `source_ko`(한국어 원문)에서 금액·시간 수치 패턴을 찾는다 — 현지어 숫자 표기까지 상대하지 않는다. warning으로 둔 이유: 숫자가 들어간 정당한 문장(연도, 학기 수)도 있어 error면 거짓 양성이 운영을 막는다. 틀렸을 때의 비용: 경고라서 사람이 무시할 수 있다 — 검토 화면(Task 7) 상단에 뜨므로 눈에는 걸린다.

## Task 5

- Important 1 — 사전의 ko 맥락 어휘 `협력`·`연계`·`합격`이 부분 문자열로 대조되어 `산학협력단`·`국제협력처`·`연계전공`·`합격자 발표`·`불합격`에 **error**로 발화한다. **고친다.** 약속을 담은 형태(`협력 관계`·`협력하여`·`업무협약`·`연계되어`·`연계하여`·`합격을 보장`·`합격 가능`)로 바꾸고, 제외 목록 방식은 쓰지 않는다(새 부서명이 나올 때마다 늘려야 한다). 이유: 사업주가 명시적으로 허용한 "한국에 어떤 대학이 있는지 소개" 게시물이 바로 이것인데 게이트가 막는다. 매달 모든 게시물에 발화하는 거짓 양성은 운영자가 게이트를 무시하게 만든다. 틀렸을 때의 비용: 약속 형태를 비껴가는 표현(`협력중`)은 빠져나간다 — 대학명후보 경고가 이름+맥락 조합을 따로 본다.
- Important 2 — `glossary.json`의 값 하나가 빈 문자열이면 `endswith("")`가 항상 참이라 error 검사가 조용히 꺼진다. **고친다.** 구현자가 금지문구 표에 대해 똑같은 위험을 이미 막아 놓고 용어집은 원시 인덱싱으로 소비했다. `validate_copy` 진입부에 같은 형태의 가드를 둔다. 틀렸을 때의 비용: 없음.

- 구현자가 내 `(?![가-힣])` 가드를 그대로 쓰지 않고 `원(?!칙|색)`을 쓴 것 — **인정.** 내 버전을 변이로 주입해 `6,800,000원입니다`의 `원` 다음이 `입`이라 주 사례가 깨지는 것을 실측해 보였다. 내가 틀렸다.

Ruling (내 지시가 틀렸다): 지난 라운드에 "ko만 고쳐라"고 한 것은 오판이었다. 구현자가 실측으로 보여 준 대로, 한국어 원문이 통과해도 그 번역이 `body_local`에서 여전히 error로 막히면 **게시물은 세 언어 어디에도 못 나간다** — 즉 ko만 고쳐서 얻은 것이 없다. 언어별 미검증 단어 목록 네 개를 고치는 대신 **구조를 바꾼다.**
- `대학맥락`을 **1인칭 주체 요구**로 재설계한다. 한 게시물에 (1) 대학명, (2) 관계 어휘, (3) **회사를 가리키는 1인칭 표지**가 모두 있을 때만 발화한다. 표지는 ko `저희`·`우리`·`당사`, vi `chúng tôi`·`chúng ta`, my `ကျွန်ုပ်တို့`, ne `हामी`·`हाम्रो`, 그리고 `glossary["company_name"]`의 해당 언어 값(네 언어 모두 검증됨). 이유: 안티골이 금지하는 것은 **우리 회사가** 없는 관계를 암시하는 것이고, 대학 자신의 제휴·협약은 사실이라 사업주가 자유롭게 말할 수 있다. 구현자가 남은 거짓 양성 목록에서 그 구분("누구의 관계인가")을 스스로 지목했다. 이 한 가지 기제가 네 언어의 같은 결함을 동시에 없애고, 대명사는 어떤 언어에서든 가장 기본적이고 검증 가능한 어휘라 미검증 조건에서도 의지할 수 있는 유일한 지점이다. 부수 효과로 맥락 어휘를 **맨 토큰으로 되돌릴 수 있어** 재현율이 오른다(`합격`만 예외 — `불합격`·`합격자 발표`는 1인칭이 붙어도 정당하므로 `합격을 보장`·`합격 가능` 유지). 틀렸을 때의 비용: 대명사 없이 관계를 암시하는 문장(`협력 대학입니다`)이 맥락 검사를 빠져나간다 — 다만 그 표현 자체는 네 언어 상시 금지 목록에 이미 있다(구현자에게 각 언어 목록에 정말 있는지 확인하라고 지시했다).
- 상시 금지 목록의 `파트너 대학`·`협약 대학`·`제휴 대학`·`협력 대학`을 **그대로 둔다.** 대학 자신의 제휴를 말하는 정당한 문장 한 가지 표현을 막는 대가를 받아들인다. 이유: 대명사 없는 명사구가 가장 위험한 형태이고, 1인칭 게이트가 구조적으로 못 잡는 유일한 형태이며, 우리 페이지에서 `파트너 대학`을 본 독자는 그것을 **우리의** 파트너로 읽는다. 사업주에게는 다른 표현(`해외 파트너십 프로그램`, `교환학생 협정 대학`)이 있다. 틀렸을 때의 비용: 대학의 교환학생 파트너를 그 단어로 소개하려면 매번 다시 써야 한다. Ruling (내 지시가 또 틀렸다): 1인칭 표지와 관계 어휘를 **같은 게시물**에서 찾으라고 한 것이 오판이었다. 구현자 실측: `저희는 한국 대학을 소개합니다. 전북대학교 산학협력단은 유학생을 지원합니다.`가 error로 발화한다 — 회사 목소리로 한국 대학을 소개하는 것은 **이 페이지의 존재 목적 그 자체**이고, 주력 게시물 거의 전부가 어딘가에 1인칭 문장을 담는다. 같은 게시물 규칙은 게이트를 다시 무시할 대상으로 만든다. **문장 단위로 좁힌다 — 단, 비대칭이다: 관계 어휘와 1인칭 표지는 같은 문장에, 대학명은 게시물 아무 데나.** 이유: `경기대학교를 소개합니다. 저희가 협력하는 대학입니다.`는 이름이 다른 문장에 있는 실제 주장이므로 셋을 모두 한 문장에 요구하면 놓친다. 문장 구분자는 네 문자 체계를 고려해 `.`·`!`·`?`·`。`·개행·`।`(데바나가리)·`။`(버마). 틀렸을 때의 비용: 문장을 걸쳐 주장하는 경우를 놓친다 — 다만 대명사 없는 두 번째 문장은 지금 설계에서도 이미 놓치고, 명사구 상시 금지가 받침이다.
- 신규 Important 1 — 한국어 1인칭 정규식이 평범한 낱말 안에서 걸린다(`해당사항`·`담당사원`·`우리 나라`·`우리 유학생`·`우리 사회`·`우리은행`). **내 지시의 결함이다.** `저희`는 한국어에서 다른 뜻이 없어 그대로, `당사`는 앞쪽 경계(선행 한글 음절 금지)를 더하고, `우리`는 **뒤에 주격·주제·소유 조사(`는`·`가`·`도`·`의`·`를`)를 요구한다.** 이유: 이 규칙이 묻는 것은 1인칭 **주체**이고 조사가 바로 그것을 표시한다. 틀렸을 때의 비용: 조사 없이 쓰는 1인칭(`우리 협력 대학`)을 놓친다 — 그 명사구는 상시 금지에 있다.
- 신규 Important 2 — **`chúng ta`는 내가 잘못 지정했다.** 베트남어의 포괄적 we(독자를 포함)라서 `Chúng ta hãy cùng tìm hiểu…`("이 대학 프로그램을 같이 살펴봅시다")가 error로 막힌다. vi 표지에서 제거하고 `chúng tôi`(배타적 we = 회사 자신)만 남긴다. 네팔어도 같은 형태(`हाम्रो देश`="우리 나라", `हामी नेपाली`="우리 네팔인")라 좁은 제외 항목 4개(`हाम्रो देश`·`हाम्रा देश`·`हामी नेपाली`·`हामी सबै`)를 **허용한다** — 부서명과 달리 국적·"우리 모두"는 이 독자층에게 작고 닫힌 집합이기 때문이다(이 구분을 README에 적게 했다). 버마어는 구현자에게 직접 확인하고 보고하게 했다.
- 신규 Important 3 — 맨 마침표로 문장을 쪼개면 한국어 날짜·URL·소수점에서 실제 주장이 끊긴다(`저희는 2026. 11. 1.부터 경기대학교와 협력합니다`가 아무 finding 없이 통과). 마침표는 **앞이 숫자가 아니고 뒤가 공백이거나 문자열 끝일 때만** 종결자다. 날짜 점은 숫자가 앞서고 URL 점은 문자가 뒤따르므로 셋 다 해소된다.
- fix round 5에서 **모델 상향·새 구현자로 바꾸지 않고 같은 구현자를 이어 쓴다.** 스킬은 라운드 4 이상에서 한 단계 위 모델의 새 구현자를 권하지만, 그 규정은 **막힌** 구현자를 상정한다. 이 구현자는 막히지 않았고 오히려 내 오류를 두 번(정규식 가드, ko-only 지시) 실측으로 잡아냈다. 이번 수정 6건은 전부 구체적으로 명시된 외과적 수정이라 새 컨텍스트가 잃을 것이 더 크다. 틀렸을 때의 비용: 같은 사각지대가 또 남을 수 있다 — 그래서 이번이 마지막 라운드이고 이후 발견은 전체 브랜치 검토로 넘긴다.
- 구현자가 넘긴 질문(`우리 회사는`·`우리들은`이 조사 요구 때문에 1인칭으로 안 잡힌다) — **닫는다.** 둘 다 실제 회사 주장이고 `source_ko`는 실제로 한국어로 작성되는 원문이다. `우리들`에 같은 조사 요구를, `우리 회사`는 조사 없이도 표지로 인정한다. 이것은 리뷰가 새로 찾은 결함이 아니라 내가 준 명세를 완성하는 답이므로 "라운드 5가 마지막"과 어긋나지 않는다.

- **Important 1 — 역번역 복사가 레이어 전체를 통과한다. 고친다.** 한 소재의 세 게시물은 `source_ko`가 **글자까지 동일**하므로(픽스처 0/1/2, 3/4/5) `back[4] = back[5] = back[3]`으로 복사하면 **finding이 0건**이다(검토자가 실행해 확인). 숫자 대조도 유사도도 그 공유 원문만 보고, `body_hash`는 `back_ko`를 항목에 묶지 않으며, Task 7의 사람도 구분할 수 없다 — 한 원문의 충실한 역번역 셋은 원래 닮아 보인다. 그러면 미얀마어·네팔어 본문이 **검사 없이 나간다.** 브리프가 이 코드의 일 중 하나로 "커버리지 확인"을 적었고, 존재·비어있지 않음은 보는데 **서로 다름은 보지 않았다.** `역번역중복`을 **warning**으로 더한다(error가 아닌 이유: 한 원문의 세 충실한 역번역이 한국어로 같은 문장에 수렴하는 것이 충분히 있을 수 있고, 거짓 error는 게시를 막는다. - **Important 2 — 숫자 순서 뒤바뀜. 동작은 유지하고 비차단 경고를 더한다.** 다중집합 비교는 순서를 무시하므로 `11월 5일`→`5월 11일`, `1.5시간`→`5.1시간`, `2026-11-05`→`2026-05-11`이 모두 finding 0건이고 문자 차이는 경고 임계값에 한참 못 미친다(검토자가 각각 실행). 순서 무시 자체는 옳다(번역에서 어순이 바뀐다) — 그러나 **양쪽이 모두 한국어**라서 순서가 어긋나는 것이 의미 있는 신호다. 검토자는 문서 수정만 권했지만 한 걸음 더 간다: **다중집합은 같은데 순서열이 다르면 `역번역수치순서` warning.** 이유: 뒤바뀐 날짜는 잘못된 마감일을 공지하는 것이고 유사도는 이를 0에 가깝게 재며 숫자 error는 볼 수 없다. 비차단이라 최악의 비용이 잡음으로 묶인다. 틀렸을 때의 비용: 절을 재배치한 정당한 역번역에 경고가 뜬다.

## 최종 재검토와 마무리

- **Minor 1 — M1의 잔여 `_require_cta`.** 두 관문이 빈칸을 서로 다른 잣대로 본다 (`validate_copy._require_glossary`는 `_non_blank`, `backtranslation._require_cta`는 `_comparable`). 문장부호뿐인 `cta.*` 값이 앞 관문을 통과하고 뒤에서 날 `ValueError`를 내 「예상하지 못한 오류 … 개발자에게 보여 주세요」로 끝난다(종료 코드 2). **현실적인 두 경우(빈 값·항목 없음)는 종료 코드 1 + 한국어 + 할 일로 옳게 끝난다 — 재검토자가 측정했다.** 닿으려면 억지 입력이 필요해 Minor다. 고치는 법 한 줄: `_require_glossary`가 `_require_cta`와 같은 빈칸 판정을 쓰게 한다.
- **Nit 3 — 문서가 찾으라고 한 낱말이 못박혀 있지 않다(기술 부채 2순위).** §5-6은 운영자에게 실패 출력에서 `유효기한이 지난 사실`을 찾으라고 그 글자를 지목하는데, M4의 시험은 키·날짜와 다른 네 문구만 보고 그 머리말은 보지 않는다. **빈 못(이 저장소의 1번 결함 부류) 여덟 번째 후보의 가장 작은 형태.** 오늘은 그 낱말이 실제로 메시지에 있어 문서는 참이므로 지금의 비용은 0에 가깝다 — 위험은 미래의 문구 수정이 조용히 문서를 낡게 하는 것. `_expired_message`를 보는 시험에 글자 하나 추가.
- **Nit 2 — 닫는 따옴표 뒤의 군더더기가 조용히 잘린다.** `FB_PAGE_TOKEN="EAA…"xyz` → `'EAA…'` (측정). I4가 닫은 재발급 고리의 더 좁은 형태. **내 브리프의 규칙("그 뒤는 버린다")과 일치하므로 구현 이탈이 아니다.** 다만 이제 애매함에는 멈추는 것이 그 함수의 규칙이 됐으니, 닫는 따옴표 뒤가 공백이거나 `#`일 때만 받는 쪽이 규칙으로 고르다.
- **Nit 4 — 「찾을 게시물」 한 줄이 중복이다.** `_report`가 결과 불명 게시물마다 번호·시각· 이미지 파일을 몇 줄 위에서 이미 찍는다. 서른 건이면 ~840자 중복. 묶음이 자족적이 되는 값은 있다.
- **Nit 5 — 수 일치와 조사.** 게시물 여섯~서른 개를 열거한 묶음 머리 뒤에서 까닭이 「이 게시물은/을」로 단수로 말한다. `_resolve_unknown`의 「그 번호의 줄의」는 「의」가 겹친다.
- **Nit 6 — M4 못의 순환성.** `_expired_message`가 시험 파일의 헬퍼이고 그것을 보는 시험이 같은 파일에 있다. 문구를 못박는 값은 있으나 변이 측정으로서는 독립적이지 않다.
